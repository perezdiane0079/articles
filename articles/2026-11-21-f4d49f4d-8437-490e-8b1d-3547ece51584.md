# 用令牌桶给任务接口做限流

<!-- content-workspace-job:f4d49f4d-8437-490e-8b1d-3547ece51584 -->

## 问题场景

任务的开放接口被合作方在整点集中调用，瞬时流量是平时的二十倍，下游直接被压垮。简单的固定窗口计数又会在窗口边界放过两倍流量。

## 实现步骤

令牌桶按固定速率补充令牌，桶容量就是允许的突发量。

```go
limiter := rate.NewLimiter(rate.Limit(100), 200)
if !limiter.Allow() {
    http.Error(w, "slow down", http.StatusTooManyRequests)
    return
}
```

按调用方维度分桶，避免一个客户把额度占满影响其他人。

```go
var (
    mu      sync.Mutex
    buckets = map[string]*rate.Limiter{}
)

func of(key string) *rate.Limiter {
    mu.Lock()
    defer mu.Unlock()
    l, ok := buckets[key]
    if !ok {
        l = rate.NewLimiter(rate.Limit(20), 40)
```

## 验证方法

以远超限额的速率压测，通过的请求数应稳定在设定速率附近。

## 注意事项

分桶表的键要设过期，否则海量调用方会把内存撑爆；限流是保护手段，被限流的请求要能快速失败，不能让它继续占用连接。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

如果数据量继续增长，需要评估对现有调用方的影响面，确保线上行为始终可控。
