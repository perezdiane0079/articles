# 用分区表归档订单表的历史数据

<!-- content-workspace-job:678f6700-7125-457d-8b38-31ff3b5f8e35 -->

## 问题场景

订单表积累了几亿行历史数据，DELETE 老数据要跑几个小时，还产生大量 WAL，删完之后磁盘空间也不释放。

## 实现步骤

按时间范围建分区，每个分区对应一个时间段。

```sql
CREATE TABLE orders_202611 PARTITION OF orders
FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

归档时把整个分区从主表摘下来，元数据操作，瞬间完成。

```sql
ALTER TABLE orders DETACH PARTITION orders_202601;
```

查分区列表确认挂载关系，摘除后主表查询自动跳过该段。

```sql
SELECT inhrelid::regclass
FROM pg_inherits WHERE inhparent = 'orders'::regclass;
```

## 注意事项

分区键必须出现在查询条件里才能裁剪，否则照样扫全部分区；主表上的唯一索引必须包含分区键，这是常见的建表失败原因。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。
