# 司机请求失败时按状态码分流重试

<!-- content-workspace-job:5b45ab06-438e-48f3-b8e5-62f1445e5e91 -->

## 问题场景

司机列表接口偶发 502，前端统一无脑重试三次，遇到参数错误时也重试，白白放大流量。

## 实现步骤

把状态码分成可重试与不可重试两类，只有 5xx 与超时进入重试。

```javascript
const RETRY = new Set([502, 503, 504]);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
```

重试间隔按指数增长并加随机抖动，避免同一时刻大量请求打到同一实例。

```javascript
async function get(url, tries = 3) {
  let last;
  for (let i = 0; i < tries; i++) {
    const res = await fetch(url);
    if (res.ok) return res.json();
    last = res.status;
    if (!RETRY.has(res.status)) break;
    await sleep(300 * 2 ** i + Math.random() * 100);
  }
  throw new Error('driver 请求失败: ' + last);
}
```

## 验证方法

用桩服务分别返回 400 与 503，前者应只请求一次，后者应按次数重试后失败。

## 注意事项

POST 请求重试要保证幂等，否则可能重复写入；登录失效类 401 不能重试，应直接跳转。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

上线初期，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。
