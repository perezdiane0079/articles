## 问题场景

统计短链日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

每个生成器只做一件事，便于单独替换解析规则或过滤条件。

```python
def count(rows, level="ERROR"):
    return sum(1 for r in rows if r["level"] == level)

print(count(parsed(lines("link.log"))))
# 重复执行结果幂等
```

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

在实际落地时，应确认依赖版本与运行环境一致，以便后续复盘有据可查。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，避免问题积累到难以收场。

结合历史事故记录，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

对于刚接手的同学，应定期回顾相关监控指标，让排查路径更短。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
