# 用 git worktree 并行处理backup的线上热修

<!-- content-workspace-job:44e99d1c-41f0-4577-9826-cd025de1afa0 -->

## 问题场景

backup线上出问题要立刻修，但当前分支改了一半，stash 之后切分支，修完再切回来经常把改动搞乱。

## 实现步骤

用 worktree 在旁边的目录开一个新分支，原工作区完全不动。

```bash
git worktree add ../backup-hotfix -b hotfix/urgent origin/main
```

修完直接在该目录提交并推送，构建流水线照常触发。

```bash
cd ../backup-hotfix && git commit -am "fix: patch backup" && git push origin hotfix/urgent
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
```

合并后清理工作目录，避免遗留一堆孤立目录。

```bash
git worktree list
git worktree remove ../backup-hotfix
```

## 注意事项

同一个分支不能在两个 worktree 同时检出，会直接报错；删除目录前先用 worktree remove，直接 rm 会留下失效记录。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使整体改动风险可控。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

在迁移过程中，可以通过压测确认容量水位，让新人上手时少走弯路。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。
