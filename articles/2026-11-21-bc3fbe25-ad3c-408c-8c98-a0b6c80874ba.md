# 优惠券表深分页查询改用延迟关联

<!-- content-workspace-job:bc3fbe25-ad3c-408c-8c98-a0b6c80874ba -->

## 问题场景

优惠券表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM coupons WHERE discount > 60 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM coupons a
JOIN (SELECT id FROM coupons WHERE discount > 60
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 该片段可重复执行，结果保持不变
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM coupons a
JOIN (SELECT id FROM coupons ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 验证方法

同一页码执行改前改后两条语句，耗时差距通常在数量级上，且返回结果完全一致。

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。
