# 订单组件的行为用轻量 DOM 测试固定下来

<!-- content-workspace-job:688404bb-4166-4e50-8c38-547f9b2c618d -->

## 问题场景

订单组件改一次样式就担心逻辑被带坏，手工点页面回归又太慢。

## 实现步骤

用 jsdom 造一个最小文档环境，把组件挂到容器上。

```javascript
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!doctype html><div id="root"></div>');
global.document = dom.window.document;
```

断言渲染出的文本、类名与事件后的状态变化，不断言具体标签结构。

```javascript
export function mount(html) {
  const root = document.querySelector('#root');
  root.innerHTML = html;
  return root;
}
```

每个用例结束后清空容器，避免上一个用例的节点影响选择器。

```javascript
const root = mount('<p class="order">订单</p>');
console.assert(root.querySelector('.order').textContent === '订单', 'render');
console.log('cases', 1, root.children.length, 500);
```

## 注意事项

jsdom 不执行真实布局，依赖尺寸的断言要改用桩值；异步渲染要用 await 或宏任务等待后再断言。

遇到复杂链路时，先把最小可复现的用例固定下来，降低同类问题再次发生的概率。

上线初期，要把异常路径和正常路径分别覆盖一遍，减少不必要的返工成本。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，避免问题积累到难以收场。

结合历史事故记录，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。
