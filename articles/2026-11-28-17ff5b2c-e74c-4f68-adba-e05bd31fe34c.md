# 报销单组件的行为用轻量 DOM 测试固定下来

## 问题场景

报销单组件改一次样式就担心逻辑被带坏，手工点页面回归又太慢。

## 实现步骤

用 jsdom 造一个最小文档环境，把组件挂到容器上。

```javascript
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!doctype html><div id="root"></div>');
global.document = dom.window.document;
```

断言渲染出的文本、类名与事件后的状态变化，不断言具体标签结构。

```javascript
export function mount(html) {
  const root = document.querySelector('#root');
  root.innerHTML = html;
  return root;
}
```

每个用例结束后清空容器，避免上一个用例的节点影响选择器。

```javascript
const root = mount('<p class="expense">报销单</p>');
console.assert(root.querySelector('.expense').textContent === '报销单', 'render');
console.log('cases', 1, root.children.length, 760);
```

## 注意事项

jsdom 不执行真实布局，依赖尺寸的断言要改用桩值；异步渲染要用 await 或宏任务等待后再断言。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

结合团队现状，可以通过压测确认容量水位，避免资源被长期占用。

上线初期，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

在实际落地时，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。
