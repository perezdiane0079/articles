# 把会话表的大事务拆成小批提交

<!-- content-workspace-job:7ebf1d8d-8ec9-4169-b968-ee575992cd3d -->

## 问题场景

会话表要一次性调整几十万行的expire_at，用一个大事务包住。执行期间锁等待严重，从库延迟飙到几分钟，失败还要整体回滚。

## 实现步骤

按主键区间切成小批，每批几千行，单独提交。

```sql
START TRANSACTION;
UPDATE sessions SET expire_at = expire_at - 1 WHERE id BETWEEN 1 AND 100000;
COMMIT;
```

每批之间留出短暂间隔，给从库和应用其他事务让路。

```sql
UPDATE sessions SET expire_at = expire_at - 1 WHERE id BETWEEN 1 AND 1000;
```

记录已处理到的最大主键，中断后从该位置继续。

```bash
for i in $(seq 0 99); do
  mysql -N -e "UPDATE sessions SET expire_at = expire_at - 1 \
    WHERE id BETWEEN $((i*1000)) AND $((i*1000+999))"
  sleep 0.05
done
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
```

## 注意事项

拆分后不再是原子操作，中途失败会留下部分已提交的数据，业务要能接受中间态或提供补偿；区间切分要基于主键而不是业务字段，后者可能重复。

在压测阶段，尽量把决策依据写进变更说明，避免资源被长期占用。

结合团队现状，可以通过压测确认容量水位，让新人上手时少走弯路。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。
