# 给支付单的 WebSocket 连接加心跳保活

<!-- content-workspace-job:7f54ad32-80f6-4a26-9df3-125ace64d126 -->

## 问题场景

支付单的实时通知经常延迟几十秒才到，客户端以为自己还连着，其实连接早已被负载均衡器静默断开，浏览器还没触发 close 事件。

## 实现步骤

客户端定时发心跳，服务端收到就回，形成双向确认。

```typescript
const ws = new WebSocket(url);
ws.onopen = () => setInterval(() => ws.send(JSON.stringify({ type: "ping" })), 25000);
```

用标记位判断上一轮是否有响应，没有就主动关闭重连。

```typescript
let alive = true;
ws.onmessage = () => { alive = true; };
setInterval(() => {
  if (!alive) ws.close();
  alive = false;
}, 60000);
```

服务端的探活间隔要小于中间设备的空闲超时，否则还是会被切断。

```typescript
wss.on("connection", (s) => {
  s.isAlive = true;
  s.on("pong", () => { s.isAlive = true; });
});
```

## 验证方法

挂机十分钟后发一条消息，应能立即收到；人为断网后客户端应在两个周期内触发重连。

## 注意事项

浏览器不会因为网络中断立刻触发 close，只靠事件判断连接状态并不可靠；心跳频率过高会增加无谓流量，通常二十到三十秒一次比较合适。

在压测阶段，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

从可观测性角度，应确认依赖版本与运行环境一致，以便后续复盘有据可查。

在跨团队协作时，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

遇到复杂链路时，优先保证失败时能快速定位原因，确保线上行为始终可控。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在迁移过程中，可以通过压测确认容量水位，便于横向对比不同方案的效果。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。
