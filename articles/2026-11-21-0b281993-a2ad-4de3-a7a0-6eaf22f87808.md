# 商品表的 JSONB 字段查询与 GIN 索引

<!-- content-workspace-job:0b281993-a2ad-4de3-a7a0-6eaf22f87808 -->

## 问题场景

商品表把扩展属性塞进 JSONB 字段，查询时用 ->> 取值再比较，数据一多就全表扫，接口从几十毫秒涨到几秒。

## 实现步骤

包含关系用 @> 判断，语义清晰且能命中 GIN 索引。

```sql
SELECT id FROM products WHERE payload @> '{"stock": 1}';
```

建 GIN 索引，注意操作符类要选对，默认支持包含与存在判断。

```sql
CREATE INDEX idx_stock ON products USING GIN (payload);
```

只取个别键时用 ->> 输出文本，需要类型转换就在表达式里显式转。

```sql
SELECT id, payload->>'stock' AS v
FROM products WHERE payload ? 'stock' LIMIT 5;
```

## 注意事项

GIN 索引写入比 B-tree 慢，更新频繁的字段要评估；jsonb_path_ops 体积更小但只支持 @>，需要键存在判断时要用默认操作符类。

从可观测性角度，应确认依赖版本与运行环境一致，让排查路径更短。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
